# Project Grader Allocation API

## Purpose

This API assigns users to semantic grading targets within a project without
moving task-creation rules out of Upload & Grading Profiles.

An allocation has one of three scopes:

- `disease_image`: image-wise grading for one disease across project sources;
- `disease_encounter`: disease-specific EncounterSet grading; or
- `encounter_set_unified`: unified person/encounter grading across diseases.

The assignable capacities are `resident` and `arbitrator`. `resident` covers
both the Resident and Resident 2 sequencing slots. Runtime grading still
prevents one user from filling both slots on the same task. An arbitrator is
also excluded from any task they previously graded as either Resident or
Resident 2; this independence rule has no cooling-off expiry.

## Authentication and scoping

All endpoints require an authenticated user with one of these application
roles:

- `admin`
- `local_admin`
- `data_manager`

Administrators may manage every lab unit. Local administrators and data
managers may read or mutate only allocations within their explicitly assigned
lab units. The allocated grader must also be assigned to the requested lab.

Browser-session mutations require the normal `X-CSRFToken` header. Requests
are JSON unless otherwise stated.

## Error contract

Errors use a stable object:

```json
{
  "success": false,
  "error": {
    "code": "grading_allocation_error",
    "message": "The grading target fields do not match the requested scope.",
    "details": {}
  }
}
```

Expected status codes are `400` for validation, `403` for lab or role scope,
`404` for missing projects/allocations/users, and `409` for duplicate or unsafe
enforcement transitions.

## Read project allocation state

`GET /api/projects/<project_id>/grader-allocations`

Query parameters:

- `include_inactive=true` includes deactivated historical allocations.

The response contains:

- the explicit project enforcement policy;
- targets derived from all active Upload & Grading Profiles linked to the
  project;
- source-profile attribution for each target;
- active resident and arbitrator coverage counts;
- scoped allocation rows; and
- configuration or missing-coverage warnings.

Example:

```json
{
  "success": true,
  "project_id": 3,
  "policy": {
    "project_id": 3,
    "enforcement_enabled": false,
    "updated_at": null
  },
  "targets": [
    {
      "key": "disease_image:1:none",
      "scope": "disease_image",
      "disease_id": 1,
      "disease_name": "DR",
      "encounter_set_type_id": null,
      "encounter_set_type_name": null,
      "label": "DR / Images",
      "grading_scheme_ids": [1],
      "source_profiles": [
        {"id": 1, "name": "Manual ZIP"},
        {"id": 7, "name": "Remidio API"}
      ],
      "coverage": {"resident": 2, "arbitrator": 1}
    }
  ],
  "allocations": [],
  "warnings": []
}
```

## Create or reactivate an allocation

`POST /api/projects/<project_id>/grader-allocations`

```json
{
  "user_id": 42,
  "lab_unit_id": 7,
  "scope": "disease_image",
  "disease_id": 1,
  "encounter_set_type_id": null,
  "capacity": "resident"
}
```

The target must currently be generated by at least one active Upload & Grading
Profile associated with the project. Submitting an existing inactive identity
reactivates the row rather than creating a duplicate.

Target field requirements:

| Scope | `disease_id` | `encounter_set_type_id` |
|---|---:|---:|
| `disease_image` | required | must be null |
| `disease_encounter` | required | required |
| `encounter_set_unified` | must be null | required |

Resident capacity requires a `resident` or `ophthalmologist` application role.
Arbitrator capacity requires `ophthalmologist`.

Successful creation returns `201`.

## Activate or deactivate an allocation

`PATCH /api/projects/<project_id>/grader-allocations/<allocation_id>`

```json
{
  "active": false
}
```

`DELETE /api/projects/<project_id>/grader-allocations/<allocation_id>` is the
REST deactivation alias. It does not physically delete the row.

## Enable or disable project enforcement

`PUT /api/projects/<project_id>/grader-allocation-policy`

```json
{
  "enforcement_enabled": true
}
```

Enabling is rejected with `409` unless:

- every disease-specific package has an unambiguous underlying disease;
- every derived active target has at least one resident allocation; and
- every derived active target has at least one arbitrator allocation.

While enforcement is absent or disabled, project-owned tasks retain the legacy
`UserDiseaseUnitRole` behavior. When enabled, the exact project, lab, semantic
target, and capacity allocation is authoritative. Tasks with no project remain
on legacy eligibility permanently.

## Runtime contract

The server derives project and target context from the task source. Clients do
not submit project, disease, or EncounterSet identifiers during grading.

```text
project task + enabled policy
    -> ProjectGraderAllocation

project task + disabled/absent policy
    -> UserDiseaseUnitRole

projectless task
    -> UserDiseaseUnitRole
```

Ambiguous source project ownership or an unresolved disease-specific encounter
context fails closed when project enforcement is enabled.
